# TUI framework research for a VS Code-like editor

Research date: 2026-08-08. Sources are limited to official project documentation, repositories, source, and release pages.

## Recommendation

Use [OpenTUI 0.5.1](https://github.com/anomalyco/opentui/releases/tag/v0.5.1) for a deliberately small, single-file editor proof if TypeScript and Bun are acceptable. It is the closest match to the intended architecture because it combines a native renderer, a real multiline edit widget, and a separate command/keymap engine with layers, conditions, discovery, and multi-stroke sequences.

Do not commit yet to “VS Code in a terminal.” OpenTUI's `Textarea` is a capable textarea, not a code-editor engine. The documented surface has one cursor/selection, undo/redo, movement, and basic edits, but no syntax-highlighted **editable** view, multi-cursor model, find/replace, folding, diagnostics/decorations, large-file guarantee, LSP client, or extension host. Its syntax-highlighted [`Code`](https://opentui.com/docs/components/code/) component is read-only. Those missing parts are most of the editor, not minor framework glue.

The first milestone should therefore be only: open one file, edit Unicode text, select, undo/redo, show dirty state, save safely, and refuse to discard unsaved changes. Use `@opentui/core` global key handlers; two commands do not justify a keymap dependency. Add `@opentui/keymap` when the first multi-stroke chord or context-sensitive binding exists. Skip React/Solid, LSP, syntax highlighting, tabs, explorer, plugins, settings UI, and integrated terminal until that slice passes the terminal and file-size gates below.

If Python is preferred, [Textual](https://textual.textualize.io/widgets/text_area/) is the fastest path to a visibly code-editor-like prototype. If the goal is a long-lived native editor and Rust is acceptable, [Ratatui](https://github.com/ratatui/ratatui) is the safer low-level foundation, but it requires substantially more editor work up front.

## The “exactly VS Code” constraint

No TUI framework can provide literal VS Code keymap parity on every terminal. The terminal and OS decide which combinations reach the process; legacy terminal input also collapses distinct keys (for example, `Tab` and `Ctrl+I`). Textual documents that Cmd/Option on macOS and the Windows key commonly never reach terminal apps. Modern terminals implementing the Kitty keyboard protocol improve modifier and key identity reporting, but cannot undo an OS-level shortcut interception. See [Textual's input guide and key aliases](https://textual.textualize.io/guide/input/) and [OpenTUI's Kitty keyboard support](https://opentui.com/docs/core-concepts/keyboard/).

The realistic target is therefore:

- Preserve VS Code **commands and editing semantics**.
- Ship the VS Code defaults when the terminal can represent them.
- Supply terminal-safe fallbacks and show the effective shortcut.
- Treat keybindings as user-overridable data with platform and context conditions.

VS Code keybindings include command IDs, multi-key chords, precedence, and `when` clauses; its editing surface also includes multi-cursor operations, find/replace, folding, and more. These are useful definitions of the compatibility target, not features inherited from a TUI toolkit. See the official [keyboard shortcut model](https://code.visualstudio.com/docs/configure/keybindings) and [basic editing feature set](https://code.visualstudio.com/docs/editing/codebasics).

## OpenTUI: what it gives us and what it does not

### Useful existing pieces

- `TextareaRenderable` already owns cursor movement, one selection, insertion/deletion, word and line operations, undo/redo, wrapping, scrolling, and content/cursor events. This is enough for a plain-text proof. [Textarea API](https://opentui.com/docs/components/textarea/)
- `@opentui/keymap` separates commands from bindings, supports focus-aware layers, priorities and conditions, pending multi-stroke sequences, active-key discovery, and command queries. That is much closer to VS Code's command/keybinding architecture than framework-local event handlers. [Keymap overview](https://opentui.com/docs/keymap/overview/)
- The OpenTUI host reports normalized keys and can opt into Kitty disambiguation, alternate-layout keys, repeat, and release. `super` is available only when the terminal reports it. [Keyboard input](https://opentui.com/docs/core-concepts/keyboard/)
- Mouse down/up/move/drag/drop/scroll, focus, paste events, terminal selection, and OSC 52 copy are built in. [Renderable events](https://opentui.com/docs/core-concepts/renderables/), [renderer integration](https://opentui.com/docs/core-concepts/renderer/)
- Production use in OpenCode is a meaningful maturity signal, but the current 0.5.x version and frequent releases still imply API churn. [OpenTUI repository](https://github.com/anomalyco/opentui), [0.5.1 release](https://github.com/anomalyco/opentui/releases/tag/v0.5.1)

### Missing editor subsystems

The following are not documented OpenTUI `Textarea` features and must not be estimated as framework configuration:

- Multiple cursors and independently directed selections.
- A scalable text model with explicit edit transactions, versioning, decorations, markers that survive edits, and documented large-file behavior.
- Editable syntax highlighting and incremental token application. Tree-sitter exists for read-only `Code`, not the textarea.
- Find/replace UI and model, regular expressions, replace-all transactions, and find history.
- Folding, bracket guides, indentation rules, auto-closing pairs, snippets, and code actions.
- Diagnostics, hover, completion, signature help, definitions, references, rename, formatting, and semantic tokens. Those require an LSP client and editor integration; VS Code's official language server guide shows the breadth of that layer. [VS Code LSP guide](https://code.visualstudio.com/api/language-extensions/language-server-extension-guide)
- Autosave/recovery, atomic writes, encoding/EOL preservation, file watching, external-change conflict handling, and hot-exit state.
- A VS Code-compatible extension host. VS Code runs extensions in isolated local/web/remote extension hosts, which is a separate product architecture. [VS Code extension host](https://code.visualstudio.com/api/advanced-topics/extension-host)
- A documented semantic accessibility or screen-reader mode.

## First proof and decision gates

Build no abstraction beyond the one-file flow. The proof should use the core renderable API and one command layer, then pass these gates:

1. **Editing correctness:** open/save without changing bytes unexpectedly; preserve configured EOL; handle empty, Unicode, emoji, combining marks, tabs, and trailing newline; protect against discarding dirty content.
2. **Representative size:** type, select, page, undo, and save smoothly in a repository-representative large file (start with 100,000 lines or the real largest expected file). Measure rather than relying on the native-core label.
3. **Shortcut matrix:** verify the required VS Code commands in at least Kitty/Ghostty, iTerm2, Windows Terminal, and one legacy terminal. Record fallbacks where Cmd/Super, Option, shifted punctuation, or chords do not arrive distinctly.
4. **Clipboard/mouse:** verify click positioning, drag selection, terminal selection override, bracketed paste, copy over local terminal and SSH/tmux, and graceful behavior when OSC 52 is rejected.
5. **IME and accessibility:** verify the target IMEs; decide whether a linear/no-animation screen-reader mode is required. OpenTUI does not supply semantic accessibility automatically.
6. **Editable highlighting spike:** before promising code-editor parity, prove that edits, selection, cursor, Tree-sitter updates, and viewport rendering can coexist without replacing `Textarea` wholesale.

If gates 2 or 6 fail, stop extending the textarea. Move to Ratatui with a purpose-built text model for the production editor, or accept Textual's Python/runtime tradeoff for the faster product. Do not build LSP, tabs, or an extension system to rescue an unproven editing core.
